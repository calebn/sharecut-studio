# Segments

A segment is a reusable piece of audio: an intro, an outro, a sponsor read or a sting. It is the audio, how its clips sit relative to each other, a level, a lane role and a ducking flag, plus an optional chapter title and transcript. The library keeps segments per user, so any episode on this machine can use them. This is issue #1777: slice 1 is the library, its file format, the `.sharecutseg` file and the `podcast segment` commands; slice 2 is Insert, which puts a saved segment on an episode's timeline (see [Insert](#insert)); slice 3 is the headless surface: the host MCP tools, `--at start|end` and `--dry-run` on insert, and a `podcast doctor` check (see [Host MCP tools](#host-mcp-tools)); slice 4 is the show kit, a saved list of segments that an episode applies in one step (see [Show kit](#show-kit)). Saving, listing, exporting and importing change no episode project.

## Copy, not link

Saving a segment copies the audio out of the episode. Moving or deleting the episode never breaks the segment, and editing the segment later never touches the episode.

## Where it lives

`PODCAST_CONFIG_DIR/segments/` (default `~/.config/podcast_mcp/segments/`):

```
segments/
  .segments.lock
  warm-intro-1a2b3c4d/
    v1/segment.json, clip-01.flac
    v2/segment.json, clip-01.flac
```

The id is the name's ASCII slug plus eight hex digits of the exact name's sha256. One name always has one id. Each version is staged in a hidden folder and lands by one rename under the library lock, so a reader never sees half a version and two writers never lose each other's.

## `segment.json`

| Field | Meaning |
|---|---|
| `schema_version` | `1`. Any other value is refused with `segment_schema_unsupported`. |
| `id`, `name`, `version` | Identity. `version` starts at 1 and the store assigns it. |
| `kind` | `intro`, `outro`, `sponsor`, `sting` or `other`. |
| `role` | The lane role (`dialogue`, `music`, `sfx`, `intro`, `outro`). |
| `fader_db` | Level of the lane. |
| `duck_under_dialogue` | Whether the lane lowers under speech. Capture sets it to false. |
| `chapter_title` | Optional chapter marker text. |
| `clips` | `audio` (a file in the segment), `offset_sec` from the segment start, `duration_sec`, `fade_in_ms`, `fade_out_ms`, `join_in_mode` and `lane`. A saved segment keeps no fade curve: capture drops a clip's `fade_in_curve` / `fade_out_curve` and an insert creates linear fades (a documented limitation; storing them is a segment schema change). |
| `transcript_words` | Optional words (`text`, `start`, `end`, seconds from the segment start). Capture does not write them yet. |
| `media` | For each audio file, its `sha256` and `bytes`. |

Unknown fields are refused. `content_sha256` is a hash of the sorted media hashes and the layout (everything except id, name and version). It is how an import recognises content it already has.

## Commands

| Command | What it does |
|---|---|
| `podcast segment save -p PROJECT --name NAME [--kind K] (--clips c1,c2 \| --range 0:00-0:22) [--role R] [--json]` | Cut the clips, or every clip overlapping the timeline range (trimmed to it), into the library as FLAC. Offsets count from the earliest selected clip, so a range that starts in silence loses its lead-in. The role and fader come from the first clip's track. A range that cuts a clip in the middle drops the fade and crossfade at the cut. Clips that overlap on one track get separate lanes. Without `--kind`: a selection starting in the first 120 s is an `intro`, one ending in the last 120 s of the timeline an `outro`, else `other`. The audio is each clip's source window with its mute regions, ignored words and clip gain baked in, as the episode renders them. It is not the full episode render: track gain, the processing chain and the transcript gate are not applied, and clip fades and joins are stored in the layout, not in the audio (an insert applies them). Clips with room-tone fills, off-speaker mutes or bleed restore are refused with `segment_render_unsupported`, because the episode would sound different. Clips under 10 ms are refused with `segment_clip_too_short`. |
| `podcast segment list [--deep] [--json]` | The newest version of each segment. Checks the manifest and audio file presence and size without reading audio content. `--deep` also verifies audio hashes and detects same-size content changes. Damage found by these checks is listed as `DAMAGED` (in `--json`, as `{"id", "version", "damaged": true, "problem", "code"}`), never hidden. Older versions are not checked. |
| `podcast segment show ID [--json]` | Layout, level and versions of one segment. |
| `podcast segment remove ID` | Delete a segment and all its versions, damaged or not. |
| `podcast segment export ID -o FILE` | Write the newest version to a `.sharecutseg` file. |
| `podcast segment import FILE [--json]` | Add a `.sharecutseg` file to the library. |
| `podcast segment insert PROJECT SEGMENT --at start\|end\|SEC [--version N] [--ripple \| --own-lane] [--dry-run] [--json]` | Insert a segment into an episode (see [Insert](#insert)). `--ripple` (the default) moves later content; `--own-lane` moves nothing and puts the segment on new tracks; both together is an error. `--dry-run` reports what would move and changes nothing. |
| `podcast segment drift PROJECT [--json]` | Which inserted segments have drifted from the library (see [Drift](#drift)). Changes nothing; exit code 0 for any report. |

`save` and `import` print one of `Saved`, `Saved a new version of` or `Already in the library`; with `--json` they print `{"status": "added" | "new_version" | "unchanged", "id", "version"}`. Failures print `Error: <message> (code <code>)` and exit 1.

The list command uses the same cheap checks with text and JSON output. `show`, import, export and insert still verify audio hashes. The host MCP `segment_list_tool` also verifies audio hashes.

## Conflict rules

- The same content as an intact stored version (same `content_sha256`, audio matching its hashes) is `unchanged`: nothing is written and the existing id and version are returned, even when the incoming file has another name. A stored version whose audio is damaged does not count: importing or saving the segment again lands as the next version and repairs the library (`segment remove` clears it for good).
- Re-importing older content after a newer version exists is `unchanged` too: any intact stored version with the same content counts, and the newer version stays the newest. The same content under a new name returns the existing id, not a new segment.
- The same name with different content is the next version. The id stays, and an earlier version is never overwritten.
- A different name with different content is a new segment at version 1.

## The `.sharecutseg` file

A zip of `segment.json`, the audio files and `MANIFEST.sha256` (`<sha256>  <name>` per other file). One segment per file. An import checks, before anything reaches the library:

- at most 64 entries and 2 GiB unpacked (checked against the headers and again while reading), 1 GiB per file, `segment.json` at most 1 MiB, the manifest at most 64 KiB, and no file compressed more than 100:1 once it is over 1 MiB;
- every entry name is a plain file name: no directories, no absolute path, no `..`, no symlinks, no repeats (names are compared ignoring case);
- the manifest lists exactly the files in the zip, and `segment.json` names exactly the audio files;
- every hash matches, and the schema version is known.

Errors: `segment_bundle_invalid` (bad zip, names, sizes or manifest), `segment_bundle_unsupported`, `segment_hash_mismatch`, `segment_schema_unsupported`, `segment_invalid` (`segment.json` is not valid or not a segment), `segment_busy` (the library lock is held), `segment_unreadable` (a file in the library cannot be read), `segment_unknown` (no such segment or version) and `segment_write_failed` (disk or permission errors). The manifest detects corruption, not forgery: anyone can repack a zip and recompute it, so an import is an integrity check, not a trust decision, and nothing is signed. Reading a stored segment (`get`, `show`, `export`) checks the audio hashes again and raises `segment_hash_mismatch` for a file that was changed or removed; `list` reports such a segment as damaged.

## Insert

`podcast segment insert PROJECT SEGMENT --at start|end|SEC` runs the `InsertSegment` document command (`segment_id`, `version?`, `at`, `placement?`), so the edit is journaled, synced and one undo step like every other timeline edit. It is host only: a share link never reaches the host's library. The code is `services/document/segment_insert.py` (audio copy and the command's service) and `edits/segment_insert.py` (the project edit).

1. The library version is read with its audio hashes checked (`segment_unknown`, `segment_hash_mismatch`). The newest version is used unless `--version` names one.
2. `--at` is `start` (0), `end` or a number of seconds, read by one parser (`segments/position.py`) for the CLI, the MCP tool and the command payload: the words ignore case and spaces, and anything else (`soon`, `1_0`, `0x10`, `nan`, `inf`, a bool) is `segment_position_out_of_range`. `end` travels in the command as the word and is resolved to the timeline end inside the document lock, so an edit saved a moment earlier is not split; a dry run resolves it the same way. The CLI and MCP always send the resolved `version` (an int), so the journal names the audio that went in; a replay inserts that version, not whichever is newest. A `--version` below 1 is `segment_version_invalid` on both paths. The `at` the journal keeps is the word `end` when `end` was asked; the result holds the second it became. The position must be on the timeline, from 0 to its end inclusive (`segment_position_out_of_range`). A project with no clips accepts 0. A copy that cannot be made or read fails with `segment_write_failed`. Insert returns `segment_media_invalid` when a clip’s audio is more than 50 ms shorter than its declared duration, the layout exceeds one day, a clip fade exceeds one hour, or a clip is shorter than one millisecond.
3. Each audio file is copied to a temporary file, its hash is checked on that copy, it is probed, and only then it is renamed to `raw/segment-<full sha256>.flac`. A file changed after the library read it is refused (`segment_hash_mismatch`) and nothing is left behind. A file already at the final name is never trusted, probed or reused: it is replaced by the verified copy. The same audio inserted twice shares one source (`seg_<sha256>`).
4. With the default placement, `ripple`, in one undoable mutation the edit opens the segment's length at `at` with the ripple `insert_gap` and `paste_segment` use (every dialogue track, plus the tracks the segment lands on), moves chapters, review comments and pending edit decisions at or after the point (a comment the point falls inside grows to cover the segment), places the clips and rebuilds the combined transcript. A clip straddling the point is split, as an `insert_gap` does. With `placement` `own_lane` (`--own-lane`) the same mutation skips the ripple, so nothing is split or shifted: no clip, chapter, review comment or pending edit moves, and every lane gets a new track (see [Own lane](#own-lane)). The chapter title, `segment_ref`, the clips' placement at `at` and the timeline duration (it grows only when the segment runs past the end) work as for `ripple`.
5. Each clip carries `segment_ref` (`segment_id`, `version`, `content_sha256` of the version inserted). [Drift](#drift) compares it with the library. A clip split or moved later keeps its `segment_ref`; a copy made by duplicate or paste does not.

**Lanes and tracks.** Lane 0 of a segment whose role is not `dialogue` goes on the project's first track of that role (an intro on the intro track the episode already has), which keeps its own fader. Every other lane, and every dialogue segment, gets a new track named for the segment (`Name`, `Name 2`, ...) with the segment's role and `fader_db`. A new dialogue track has the segment name as its label and speaker, since a sponsor read is not one of the episode's speakers. If a track or speaker already goes by that name (compared ignoring case), the new track is called `Name (segment)` instead, so speaker-keyed edits never merge the segment into a real speaker. The new dialogue track still joins every dialogue ripple.

**Own lane.** `placement` is `ripple` (the default, everything above) or `own_lane`, for music under dialogue. With `own_lane` nothing already in the episode changes: a dialogue clip across `at` is not split, later clips, chapters, comments and pending edits stay where they are, and the segment's chapter title is added at `at`. No lane reuses an existing track, not even lane 0 of an intro or music segment: every lane gets a new track (`Name`, `Name 2`, ... or `Name (segment)` when the label is taken, ids from the same slug rule), with the segment's role and `fader_db`. So the segment plays over the dialogue it overlaps and shares no track with older clips. Inserting it again adds more tracks. The report is derived from a trial run as for `ripple`, so `clips_moved`, `chapters_moved`, `comments_moved` and `pending_edits_moved` come out empty, the applied result's `affected_tracks` is empty and `tracks_added` lists the new tracks. A dialogue-role segment is refused with `segment_placement_unsupported`: it would become a speaker track, join every later ripple and trigger ducking. Any other `placement` text is `segment_placement_invalid`. **The new lane plays at full level until it is ducked.** Insert does not duck: run `ApplyDucking` (MCP `apply_ducking_tool`, CLI `podcast edit duck`), which ducks a music-role lane by default, with or without `duck_under_dialogue`; a lane of another role (an intro, outro or sound segment) ducks only when its segment was saved with that flag or the lane is named ([envelopes.md § Ducking](envelopes.md#ducking)). The report and journal carry `placement` only for `own_lane`; a `ripple` insert writes exactly the bytes it did before the option existed. The kit apply always uses `ripple`.

**Mixing.** A segment lane (a track with no recording whose clips came from a segment) is rendered to its own stem and mixed into the premix, bounces, previews, exports and share range audio, with the clip offsets, fades, the track's volume fader and mute, and any envelope on it. An `own_lane` segment that runs past the dialogue makes the premix longer. Notes:

- The mix fade settings (`mix.fade_in_sec`, `mix.fade_out_sec`) apply only to music, intro and outro tracks that have a recording. A segment lane has only its clips' own fades, so a segment at the very start or end of the episode starts and stops at its clip edges without the 2 s and 3 s fades. The mix step leaves a lane's own envelope, ducking included, untouched, but it re-renders a lane stem that went stale (a dip applied since the last render) before it mixes, so `podcast pipeline run --only mix_with_music` right after ducking applies the dip; the summary says `1 segment lane stem refreshed` or `N segment lane stems refreshed`. Fresh stems are not re-rendered.
- The headroom trim counts the lane: a loud segment lowers the trim for the whole mix.
- A ripple dialogue segment is mixed at its own level; it is not loudness balanced with the recorded dialogue tracks.
- Whether an insert makes the transcript reconciliation stale follows what it changes. A ripple insert of a non-dialogue segment at or after the end of the dialogue moves no dialogue clip and leaves a fresh reconciliation fresh. An insert that moves or splits dialogue (an intro at the start, one inside speech or between clips) marks it stale, because the noise floors, the other track's window and the volume envelopes all change. A dialogue segment, which adds a speaker, always marks it stale. An own-lane insert moves nothing and never does.
- After an insert, export and guest range playback need a refreshed mix (export refuses a stale mix with `stale_mix`, a guest range with `mix_out_of_date`). `podcast render-preview` or a pipeline run refreshes it.
- A lane whose segment audio file is gone fails the render with `segment_source_missing`, naming the lane. Re-insert the segment or restore the file.
- A project that already has segment lanes re-mixes once on the first mix after this change.

**What stays put (ripple).** Music and sfx tracks the segment does not land on do not ripple (the same scope as `insert_gap`), so a music bed spanning the point stays continuous. The inserted audio has no transcript words, so text-based edits see no words there. Project names, hashes and the copied audio live in the project, which a share guest receives; the library itself and the `InsertSegment` command stay host only.

**What is applied.** The clips' source windows, offsets, fades and join modes. The segment's `chapter_title`, when it has one, becomes a chapter marker at `at`. `duck_under_dialogue` is stored in the library, not copied into the project. `ApplyDucking` reads it from the library through each clip's `segment_ref` when it picks non-music tracks to duck (a music lane ducks by role, with no library read), so a library edit after the insert shows only on the next ducking run ([envelopes.md § Ducking](envelopes.md#ducking)).

Project format and replay (`placement`): no model field changes, so `schemas/episode.project.shape.lock.json` is untouched and `scripts/project_compat.py check` passes. The value is written only for `own_lane`, inside dict content that has no shape: `DocumentSyncSection.last_command.payload` and `HistoryEntry.params` are free-form dicts (history rows already hold per-operation keys), and a `ripple` insert omits the key, so its bytes are unchanged. Under the [compatibility boundary](project-format.md#compatibility-boundary) that is neither a structural shape change nor a new field, so the project version stays `2.5` with no upgrade step. Limit: undo and redo restore snapshots, not commands, so they never re-run an insert; but a build older than this one that re-applies a journaled `own_lane` command ignores the unknown `placement` key and would ripple, and a replayed project would then differ. The repo has no replay guard for unknown payload keys to extend, so this is documented, not blocked. For `segment_ref` (added earlier, when the version was `2.0`): `Clip.segment_ref` is optional and absent from a clip that has none, so existing projects load and save unchanged, and the shape lock was refreshed then.

## Drift

`podcast segment drift PROJECT [--json]`, MCP `segment_drift_tool(project_path)` and `GET /api/segments/drift?path=` (which, like the other path routes, pins the served project when it allows one) answer one question: which segments inserted into this episode no longer match the library. All three call `report_segment_drift` in `services/document/segment_drift.py`, so the JSON and the codes are the same. The project is opened with `ProjectWorkspace.open(path, adopt=False)`: nothing is written or journaled, and a workspace under its retired entry-file name is not renamed. There is no auto-update and no "update this segment" command.

Identity is content first. A clip's `segment_ref` is `(segment_id, version, content_sha256)`; the version number alone is not stable, because a hand delete or a remove and re-import can reuse it. The report has one row per distinct ref, sorted by that triple: `ref`, `state`, `library_version` (the newest version number in the library, or null, even when that version is the damaged one), `clips` (ids of the clips carrying the ref) and, for `missing` and `damaged` only, `code` and `problem`.

The first rule that matches decides the state:

1. `missing`: the segment has no versions in the library (`segment_unknown`, "There is no segment called X"; also a hand-edited invalid id).
2. `damaged`: the newest version, or the ref's own version when the library lists it, fails the cheap check. The row carries the code the store raised, unchanged: `segment_invalid`, `segment_schema_unsupported`, `segment_unreadable` or `segment_hash_mismatch`, and the problem names the version. If the ref's own copy is damaged while the newest is current, the row is damaged.
3. `current`: the newest version's `content_sha256` equals the ref's, whatever its number.
4. `missing`: the ref's version number is not in the library (`segment_unknown`, "Version N is not in the library").
5. `changed`: the ref's version exists and its content differs from the ref.
6. `newer`: the ref's version exists with the ref's content and the newest version's content differs.

Examples: ref v2 with only v1 and v3 stored is `missing`; ref v3 after a re-import as v1 with other content is `missing`; ref v1 content A when A was re-imported as v3 is `current`; ref v1 other content with a v2 stored is `changed`.

The check reads `segment.json` and file sizes only, never audio hashes, so `current` means the library's record matches, not that the audio is verified. A segment removed while the call runs is classified again from a fresh version list. If a segment's version list cannot be read after three tries (an `OSError`), its refs are left out of the report, as `scan()` leaves that segment out; if a version vanishes on the last try, the ref is `missing` with `segment_unknown`. A project that parses but is not a valid project is refused with `project_unreadable` on the CLI, MCP and HTTP, as a file that is not JSON is. `segments/drift.py` is the pure classifier and `drift_rows` in `segments/summary.py` builds the rows.

## Host MCP tools

Five tools mirror the CLI for a host agent: `segment_list_tool`, `segment_show_tool`, `segment_save_tool` (`clip_ids` or `time_range`, plus `name`, `kind`, `role`), `segment_insert_tool` (`project_path`, `segment_id`, `at` as `"start"`, `"end"` or seconds, `version`, `dry_run`, `placement` as `"ripple"` (default) or `"own_lane"`) and `segment_drift_tool` (`project_path`, read-only, see [Drift](#drift)). They live in `mcp/tools/segments.py` and use the same services as the CLI, so errors carry the same codes. They are host only: the guest share MCP has an explicit tool allowlist and none of these is on it, and `InsertSegment` stays out of every share role's document commands (`tests/test_segments_insert.py` covers both).

`segment_insert_tool` submits `InsertSegment` on the document plane as `mcp:host`, so the edit is journaled, reaches an open Studio tab and is one undo step. It is applied, not held as a pending proposal: pending proposals in this codebase are `EditDecision` records of type remove, mute or split, which the host approves or rejects, and an insert that opens time and adds tracks and sources has no such record. Call it with `dry_run=true` first. The report holds `timeline_duration_before_sec` and `timeline_duration_after_sec`, `clips_moved`, `clips_added` (split halves included), `chapters_moved`, `chapter_added`, `comments_moved`, `pending_edits_moved`, `tracks_added` and the lane to track map. It is computed on a copy of the project with the library audio hash-checked and probed in place (read-only), so a clip whose audio is more than 50 ms shorter than its declared duration is refused as the real insert refuses it (`segment_media_invalid`), and nothing is written, journaled or added to `raw/`. The project is read where it is: a workspace still under its retired entry-file name (see `project-format.md`) is not renamed by a dry run, `segment_save_tool` or `podcast segment save`. The CLI JSON and MCP reports give clip counts. They omit the IDs of the new clips. The real insert result carries `dry_run: false`. A `time_range` such as `0:00-1:15` takes minutes and seconds below 60 and at most 24 hours (`segment_range_invalid`).

## Studio routes

Studio reaches the library over HTTP. The routes are adapters on the same services as the CLI and the host MCP tools (`library_rows`, `show_segment`, `save_segment`, `SegmentStore`); they add no segment rules of their own. They are host only: a foreign Origin or Host, or a relayed (guest) request, is refused, and a guest share never reaches the library.

| Route | Does |
|---|---|
| `GET /api/segments` | The newest version of each segment, with a `damaged` row for each unreadable one (same rows as `segment list --json`). |
| `GET /api/segments/drift?path=` | The [drift](#drift) rows for the episode at `path` (host only, the project path is checked like `POST /api/segments`). Declared before `{id}` so it is not read as a segment id. |
| `GET /api/segments/{id}` | One segment with its `versions`. |
| `GET /api/segments/{id}/insert-preview?path=&at=&version=&placement=` | The dry run of [Insert](#insert) for the episode at `path` (host only, the project path is checked like `POST /api/segments`): the same report as `segment insert --dry-run --json` (`clips_moved`, `chapters_moved`, `comments_moved`, `tracks_added`, `timeline_duration_after_sec`, ...). `at` is `start`, `end` or seconds; `placement` is `ripple` (default) or `own_lane`, and anything else is a 400 `segment_placement_invalid` (a dialogue segment with `own_lane` is 400 `segment_placement_unsupported`). It opens the project with `adopt=False` and writes nothing to the episode or the library. Refusals carry the insert's own codes (`segment_unknown` 404, `segment_position_out_of_range`, `segment_version_invalid`, `segment_media_invalid`, `segment_hash_mismatch`, `segment_unreadable` 400, `segment_write_failed` 500; a `version` below 1 is a 400 `segment_version_invalid` here, not the audio route's 422). |
| `GET /api/segments/{id}/audio?clip=N&version=V` | One clip's audio file as `audio/flac`, `Cache-Control: no-store`. `clip` is an index from 0, `version` from 1 (newest when omitted). |
| `POST /api/segments` | Save clips of an episode: `path`, `name`, then `clip_ids` or `time_range` (`0:00-0:22`), optional `kind` and `role`. Returns `{status, id, version}`. |
| `DELETE /api/segments/{id}` | Remove every version. Returns `{"removed": id}`. |
| `GET /api/segments/{id}/export` | The newest version as one `<name>.sharecutseg` file: `application/zip`, `Content-Disposition: attachment`, `Cache-Control: no-store`. The file name is the segment id without its hash, limited to `[A-Za-z0-9._-]`, never raw segment text. It is built with `export_segments` in a private temp folder that is removed after the response. |
| `POST /api/segments/import/preview` | The file as the raw request body (`application/octet-stream`, no multipart). Streams it to a private staging file, runs every check of `import_bundle` without touching the library and returns `{token, name, kind, duration_sec, clip_count, outcome, version, existing_id}`. `outcome` is `added`, `unchanged` or `new_version`; `version` is the one the add would give; `existing_id` is null for `added`. |
| `GET /api/segments/import/{staged_id}/audio?clip=N` | One clip of a staged file as `audio/flac`, with ranges, for the preview's play button. |
| `POST /api/segments/import` | `{token}`. Adds the staged file with `import_bundle` (which checks every hash again) and clears it. Returns `{status, id, version}`. |
| `DELETE /api/segments/import/{staged_id}` | Cancel: removes the staged file. An unknown token is not an error. |

Every refusal carries the service's own code in `X-Sharecut-Error-Code`. Status map: `segment_unknown` 404, `segment_import_unknown` 404, `segment_busy` 409, `segment_upload_too_large` 413, `segment_bundle_too_large` 422, `segment_staging_full` 429, `segment_import_committing` 409, `segment_no_room` 507, `segment_write_failed` 500, everything else 400 (`segment_hash_mismatch` stays 400). The import routes (preview and commit) answer 422 for a file that is not a valid bundle: `segment_bundle_invalid`, `segment_hash_mismatch`, `segment_schema_unsupported` and `segment_invalid`. A `clip` or `version` out of range for a segment that exists is `segment_unknown` 404; `clip=-1` or `version=0` is a 422.

Each clip is its own already-trimmed FLAC, served whole. The route previews one clip at a time.

### Import staging and limits

An import is two steps so nothing reaches the library before the person has seen what it is. The preview route writes the body in blocks to `<library>/.staging/<token>.partial` (folder `0700`, files `0600`) and checks it with the same `_verify_bundle` that `import_bundle` runs, so a file the preview accepts is a file the import accepts. Only a checked file is renamed to `<token>.sharecutseg`; any failure, a too-large body or a dropped connection removes the partial file. The zip stays whole: a clip played in the preview is copied beside it on first request, and nothing is unpacked into the library until the commit. The check itself unpacks the entries into a private folder in the system temp directory (up to 2 GiB, removed afterwards), so it first requires that folder's disk to have room for the headers' summed size (`segment_no_room`, 507).

- **Cap.** The zip is at most 1 GiB (`MAX_BUNDLE_BYTES`), below the 2 GiB unpacked limit. A larger `Content-Length` is `segment_upload_too_large` (413) before a byte is read, and a body that outgrows the cap while streaming is the same. `podcast segment export` and the export route use the same constant, and export runs the import's entry checks (at most 64 entries, per-entry size, compression ratio) on the file it wrote: a segment whose file would be refused is itself refused with `segment_bundle_too_large` (the file is removed), so a file the app writes is never refused by its own import. `MaxBodySizeMiddleware` caps every other POST at 4 MiB by default (`PODCAST_GUI_MAX_BODY_BYTES` changes it); the preview path is the one exemption (`SEGMENT_IMPORT_PREVIEW_PATH` in `util/body_limits.py`), and the route enforces its own cap.
- **Token.** 128 random bits as 32 lowercase hex characters, matched in full before any path is built. Anything else, a token that expired and a token already committed are `segment_import_unknown` (404).
- **Waiting files.** At most 4 at a time. When all are taken the oldest staged file is removed to make room, so an abandoned preview never locks the person out (`segment_staging_full`, 429, only when all four are uploads still in progress). The count check and the creation of the partial file run under one lock. The preview refuses when the folder's disk has less than three times the declared size free, and a chunked upload with no `Content-Length` is checked against free space as it grows (`segment_no_room`, 507). A file whose client has gone by the end of the upload is discarded. A file waits at most one hour (`STAGED_TTL_SEC`); every preview, commit and cancel sweeps the older ones, together with their clip copies and any partial file.
- **Commit.** The token is claimed by renaming the staged file to a private name before the import runs, so two commits of one token cannot both add it; the second is `segment_import_unknown`. Only the commit takes the library lock. `segment_busy` (409) puts the file back so the person can try again; any other failure (a file that does not verify) removes it. A cancel while the commit runs is `segment_import_committing` (409). The preview never waits on the lock. The outcome shown in the preview can be stale by the time of the commit (another program may have added the same segment), so Studio reports what the commit returned.

The kit offer is `GET /api/kits/offer?path=` (host only, like drift; the web client is `gui/web/src/api/kits.ts`, `loadKitOffer`). Studio offers the show kit in the frame's alert slot and applies it with `POST /api/kits/apply` (see Apply route and Studio notice under Offer below); the CLI and MCP keep `kit apply` and `kit_apply_tool`.

The web client is `gui/web/src/api/segments.ts` (`loadSegments`, `loadSegment`, `loadSegmentDrift`, `saveSegment`, `removeSegment`, `segmentAudioUrl`, `previewSegmentImport` (the file as the raw body), `commitSegmentImport`, `cancelSegmentImport`, `stagedClipUrl`, `downloadSegmentFile`, `previewSegmentInsert` for the dry run route, and `insertSegment`, which submits the `InsertSegment` document command through `api/documentEdits.ts` so the insert is queued, synced and one undo step; `segmentInsertRefusal` names the refusal code of a failed insert or preview). `insertSegment` resolves to `{queued: false, applied, historyHead}` or `{queued: true, historyHead: null}`. A card should pass the preview's `segment_version` into the insert so the user applies what they saw, and show the apply reply's `at` and `duration_sec`, not the preview's, since `end` is resolved under the document lock.

## Studio

Studio shows the library in two places, both reading `GET /api/segments` through `gui/web/src/api/segments.ts` and living in `gui/web/src/segments/`:

- **Home.** A Segment library section after Recent, owned by `HomeScreen` (it holds the `useSegmentLibrary` hook and hands `HomeView` a `library` slot). It is a real table on a wide Home and a list on a narrow one. On a first-run Home with no episodes and no segments it stays out of the way; with segments it shows.
- **Settings.** A Segment library row in the Settings sheet (`chrome.segmentLibraryOpen`) opens `SegmentLibrarySheet`, a bottom sheet on a phone and the end-edge sheet elsewhere. Settings also opens inside an episode, so `dawApp` mounts the sheet too, without waiting for `syncEnabled`. The sheet reads the list only while open.

A row shows the name, `v{version}` (with `· N versions` only when there is more than one), the kind, and a length computed from the clips (the end of the last clip; the list rows carry no `duration_sec`). Studio does not show "Used in N episodes": the library records no usage.

**Audition.** Play uses one module-level `HTMLAudioElement` shared by the Home section and the sheet, with `preload="none"`, started only from the click handler (a phone starts audio only from a tap). The URL is built at the click with `segmentAudioUrl`, so a rotated session token is never stale, and it is never written into the page text. A segment with several clips plays them in order (`ended` moves to the next, the last one stops). Audition stops when another row starts, on a second tap, on `ended` or `error`, when the section unmounts, when the sheet closes and on `pagehide`. A refused or failed play says "Couldn't play this segment" on that row. It does not take the transport's playback session.

**Remove.** More, then Remove from library, swaps the row for the inline confirm: it says it removes the segment ("all N versions" when it has more than one, and for a damaged row every version), that this cannot be undone and that episodes already using the segment keep their copy (insert copies the audio into the episode). Keep is focused and Escape is Keep. There is no Undo: `DELETE /api/segments/{id}` is outside project history. Afterwards a status line says what was removed and focus moves to the next row (or the empty message). A `segment_busy` 409 restores the row with "Another action is using this segment. Try again."; a 404 counts as already removed.

**Export and import.** More has Export as file on a readable row: it fetches `GET /api/segments/{id}/export`, shares the file with the share sheet where the browser can share files on a touch device, and otherwise downloads it. The share needs a recent tap and the file is fetched first, so a browser may refuse it; the file is then saved and the status line says so. The Export item is hidden from guests, a second tap while one export prepares is ignored, and the status line always ends in a result (shared, saved, cancelled or the failure). Import (a native button above the list and in the empty library, accepting `.sharecutseg,application/zip`, or a file dropped on the list, matched by the `.sharecutseg` extension or the zip type; every file drag over the list is claimed so the browser never opens it, and a drop while busy or on the preview sheet is refused or ignored) uploads the file to `POST /api/segments/import/preview` and shows a bottom sheet (a centered card on a desktop) with the name, kind, length, Play for the staged clip and one line: "Adds {name}", "Adds as {name} v{n}" or "Already in your library". Add to library commits the token (Show in library for a file already there, which cancels the staged file and marks the row, with no commit). The toast reports what the commit returned, which can differ from the preview if the library changed in between, and the list reloads with the row highlighted. A refused file shows the service message in the sheet and adds nothing; a busy library keeps the sheet open with the reason so Add can be tried again. Guests see no Import or Export.

**Damaged rows** are listed, never hidden: a warning chip ("Can't be played or inserted"), the id and the `problem`, no Play, and Remove only.

Loading is a skeleton after 300 ms, a failed read shows the reason with Try again, and the empty state does not promise a way to save. Palette commands for the library are not in this slice.

**Save as segment.** The Edit stage's More menu (host only) has a Save as segment row for a clip selection or a range. It runs the `segment.save` command, which sets `chrome.saveSegmentOpen`; `stage/edit/SaveSegmentHost.tsx` shows `SaveSegmentCard` (an anchored popover beside the selection on desktop, a bottom sheet on a phone) with a Name, a Kind and a line such as "3 clips, 0:22". `edit/segmentSelection.ts` maps the selection to `saveSegment`:

- Clips (one or several) send `clip_ids`. The summary counts those clips and spans the earliest start to the latest end.
- A range, or words that resolve to one exact range, sends `time_range` as `start-end` in seconds with three decimals, and needs exactly one stretch of time. The server captures every track in that span, so a range that leaves out a track that has audio in it is refused ("A segment keeps every track") instead of saving more than was selected.
- `role` is not sent, so the server takes it from the first clip's track.
- No route exposes `guess_kind`, so the card repeats it: the selection starting within the first 120 s is Intro, ending within the last 120 s of the timeline is Outro, else Other (`SEGMENT_EDGE_SEC` matches `EDGE_SEC` in `segment_capture.py`). The chosen kind is always sent, so the saved kind is the one the card showed.

The toast reads "Saved {name} to your library" (`added`), "Saved {name} as version {n}" (`new_version`) or "{name} is already in your library" (`unchanged`), with no Undo. `segmentSaveRefusal` names the codes `segment_clip_too_short`, `segment_render_unsupported`, `segment_busy`, `segment_write_failed`, `segment_invalid` and `segment_name_invalid` (a name with no ASCII letter or digit, which the library cannot turn into an id); each has a plain sentence (`edit/segmentSaveMessages.ts`) shown in the card, which stays open. Any other failure says "That did not save. Try again."

**Insert segment.** The host's Action bar has an Insert segment item when only the playhead is set, and a More row for a clip or a range. Both run the `segment.insert` command (host only, not a palette row, no key), which sets `chrome.insertSegmentOpen`; `stage/edit/InsertSegmentHost.tsx` shows `InsertSegmentCard` (an anchored popover on desktop, a bottom sheet on a phone). On the phone both cards pass Cancel and the primary to the sheet footer (`form={useId()}` ties the footer submit to the form, so Enter in a field still submits); anchored, they stay in the form. On a screen shorter than 40 rem the sheet opens full, and below 22 rem (`stages/edit/useCrampedSheet.ts`, measured in root em so large text counts) the actions return to the end of the form. Both cards share `SegmentCardFrame` and keep their form state above it, so crossing the phone and desktop breakpoint with a card open keeps the name, the pick and a save or insert in flight.

- The list comes from `loadSegments` when the card opens. A damaged row shows its problem and cannot be picked. An empty library says "Your library is empty. Save clips as a segment first, with Save as segment in the More menu."
- Position is At start, At end or At playhead. It starts from the kind (`intro` is start, `outro` is end, else playhead) until the person picks one. The request carries `"start"`, `"end"` or the playhead in seconds (three decimals); a playhead at or past the end of the timeline is sent as `"end"`. The playhead is read when the card opens.
- Every change of segment or position calls `previewSegmentInsert` with an `AbortSignal`; a late reply for an earlier choice is dropped, and Insert is off until the preview for the current choice is back. The preview reads the saved file, so the card labels it "Preview, from the saved episode". It says what is added and where, how many clips, chapters, comments and pending edits move later (or "Nothing moves."), "Adds a new lane." for `tracks_added` (never a track id) and the new length. For own lane it reads from the requested placement: "Adds 0:22 at 0:00 on a new track.", "Nothing already in the episode moves.", a ducking line from the library row (`duck_under_dialogue` true: "It plays at full level over the voices. Ducking is a separate step (podcast edit duck)."; a music segment otherwise: "It plays at full level until you run ducking (podcast edit duck), which lowers music under speech."; any other role: "It plays at full level. It was not saved to duck under dialogue."; the card never says it will be ducked, since insert itself never ducks and only `ApplyDucking` does) and "The episode becomes 10:22 long.".
- Between the list and Position, once a segment is picked, a native radio group (fieldset legend "What happens to the episode", `sys-segment-option` rows, 44 px on a phone) offers "Move the rest later" (`ripple`: "Later clips, chapters and comments shift by the segment's length.") and "Play over the episode" (`own_lane`: "Nothing moves. The segment is added on new tracks of its own."). It is not shown before a pick or for an empty library. The default comes from `defaultPlacement(row)` in `edit/segmentInsertMessages.ts`: a `music` segment starts on Play over the episode (a bed plays under the show, so nothing should move), every other role starts on Move the rest later, and a dialogue segment is always Move the rest later. It does not read `duck_under_dialogue`. A pick wins over the default. The server and the CLI and MCP tools still default to `ripple`. Unlike Position, the choice resets to the default whenever another segment is picked, because it describes the segment (a music bed versus a sponsor read). A `dialogue`-role segment (the library row carries `role` and `duck_under_dialogue`) has Play over the episode disabled with the visible text "Dialogue segments always move later content. They cannot have their own lane."; a checked own lane resets to Move the rest later. The label never says "Music under dialogue", which would promise ducking. The placement is part of the preview key (`id|at|placement|round`), so a change turns Insert off until the new preview is back. The card sends `placement: "own_lane"` in the preview query and the insert request only for own lane and omits it for ripple, as the server treats a missing key as `ripple`.
- `insertSegment` passes the preview's `segment_version`. The toast shows the apply reply's `at` and `duration_sec` ("Inserted Cold open: 0:22 at 0:00"; "Inserted Warm bed over the episode: 0:22 at 0:00" when the reply's `placement` is `own_lane`) and offers Undo with the reply's history head. With no head there is no Undo. A queued reply (held offline until reconnect) says "Insert of Cold open queued. Reconnect to send it.", with no Undo and no claim that anything moved.
- `segmentInsertRefusal` names `segment_unknown`, `segment_version_invalid`, `segment_unreadable`, `segment_busy`, `segment_hash_mismatch`, `segment_media_invalid`, `segment_write_failed`, `segment_position_out_of_range`, `segment_placement_unsupported` ("Dialogue segments cannot have their own lane. Choose Move the rest later.", which also resets the choice to ripple) and `segment_placement_invalid` ("That placement is not available. Pick a placement again."); each has a plain sentence (`edit/segmentInsertMessages.ts`) shown in the card, which stays open. Any other failure says "That did not insert. Try again." While an insert runs, Escape, Cancel and the scrim do nothing.

## Show kit

A kit is an ordered list of library segments with where each goes, for example an intro at the start and an outro at the end. A new episode applies it in one command. The kit is offered, never applied by itself: nothing in the app applies a kit unless someone runs `kit apply` or calls `kit_apply_tool`. Inserting at `start` ripples later audio, as every insert does.

**Where it lives.** `PODCAST_CONFIG_DIR/kits/` (default `~/.config/podcast_mcp/kits/`), beside the segment library, with the same conventions: `<id>/v<N>/kit.json`, an id that is the name's slug plus eight hex digits of the exact name's sha256, a version assigned by the store, a version staged in a hidden folder and landed by one rename under `.kits.lock`. The same name with other entries is the next version; entries equal to the newest version are `unchanged`. Only the newest version counts, because it is the one `kit apply` uses: saving an older list again is a new version, not a report of the old one. An earlier version is never overwritten. A name is at most 200 characters and a note 500. A kit holds no audio, only segment ids.

**`kit.json`.**

| Field | Meaning |
|---|---|
| `schema_version` | `1`. Any other value is refused with `kit_schema_unsupported`. |
| `id`, `name`, `version` | Identity, as for a segment. |
| `entries` | 1 to 32, in the order they are applied. Each: `segment_id`, `version` (a whole number pins that segment version; `null` means the newest when the kit is applied), `at` (`start`, `end` or seconds, read by `segments/position.py` like `--at`, never negative) and an optional `note`. |

Unknown fields are refused (`kit_invalid`). The content hash covers the entries only, so a rename is a new kit (a new id), the same as for segments.

**Commands.**

| Command | What it does |
|---|---|
| `podcast kit save NAME -s SEGMENT[@VERSION][:AT] ... [--json]` | Save a kit. `AT` is `start` (the default), `end` or a second. Every segment, and every pinned version, must be in the library (`kit_segment_missing` names each one that is not). |
| `podcast kit list [--json]` | The newest version of each kit, with how many of its segments are missing from the library. A kit whose newest version cannot be read is listed `DAMAGED`. |
| `podcast kit show ID [--json]` | The entries in order, with whether each segment is present. |
| `podcast kit remove ID` | Delete a kit and all its versions. Its segments stay. |
| `podcast kit export ID -o FILE` | Write the newest version and the segment versions it uses to a `.sharecutkit` file. |
| `podcast kit import FILE [--on-conflict skip\|new-version] [--json]` | Add the file's missing segments and its kit to the library. |
| `podcast kit apply ID PROJECT [--dry-run] [--json]` | Apply every entry to an episode (see below). |
| `podcast kit offer PROJECT [--json]` | Whether the episode should be offered a kit, and which kits it can offer (see Offer below). Changes nothing; exit code 0 for any report. |

**`.sharecutkit`.** A zip of `kit.json`, `MANIFEST.sha256` and, for each segment version the kit uses, that segment's `segment.json` and audio as flat entries named `segNN__<file>` (a segment version used by two entries is stored once; the issue's "segments plus the layout" is `kit.json`). Each segment id and version pair has exactly one bundled member, even when two members have identical content. Repeated kit entries can reference that shared member. An import refuses a duplicate pair with `kit_bundle_invalid` before audio unpacking or library writes. An import runs the `.sharecutseg` checks, with the cap raised from 64 to 290 files (`kit.json`, the manifest and 32 segments of a `segment.json` and up to 8 audio files each; more than that per segment is refused) and the compression-ratio check applied from 64 KiB instead of 1 MiB: plain entry names only (the only shape is `kit.json`, the manifest or `segNN__name`), no repeats ignoring case, no symlinks, sizes against the headers and while reading, 2 GiB unpacked, `kit.json` and each `segment.json` at most 1 MiB, no file over 100:1 compression once it is over 1 MiB, a manifest that lists exactly the files, every hash matching, each segment folder holding exactly the audio its `segment.json` names, and every kit entry naming a segment (and version) that is in the file. The order is: headers; then `kit.json`, the manifest and every `segment.json` are read straight from the zip and checked against each other (hashes, the kit id against its name, each segment id against its name, each segment's files against the audio it names, every kit entry against a bundled segment, and every bundled segment against a kit entry, so a file cannot carry segments the kit does not name); only then is audio unpacked, with a budget of the declared sizes, and hashed. These archive-admission checks finish before library writes. A later per-segment validation or library failure can leave earlier segments added. Errors: `kit_bundle_invalid`, `kit_hash_mismatch`, `kit_schema_unsupported`, `kit_invalid` (`kit.json` is not a kit), `kit_write_failed` and `kit_busy` (a segment-library lock or write failure during import is said in these), plus `kit_unknown`, `kit_unreadable`, `kit_name_invalid`, `kit_segment_missing` and `kit_on_conflict_invalid`. Like `.sharecutseg`, the manifest is an integrity check, not a signature.

**Import.** Each segment goes through the library's own dedupe (`added`, `unchanged` or `new_version`; the same audio under another name returns the existing id). A pinned `version` in the file is rewritten to the version the segment has in this library, because version numbers belong to a library. The kit is then stored under `--on-conflict`: `new-version` (the default) stores it as the next version when a kit of that id has other entries, `skip` leaves the existing kit as it is and reports `skipped`; the file's segments are still added, since they never overwrite anything. Importing the same file again changes nothing (every status is `unchanged`).

**Apply.** `podcast kit apply ID PROJECT` (and `kit_apply_tool`) first refuses, before anything is written: an unknown kit (`kit_unknown`); every entry whose segment or pinned version is not in the library, all named in one `kit_segment_missing` message; a segment whose audio changed (`segment_hash_mismatch`); and any refusal the whole kit meets when it is run on a copy of the project (`segment_position_out_of_range`, `segment_media_invalid`; the message says which entry and that nothing was changed). The copy does not run the document service's own write path, so that is not a guarantee against a failure of the write itself. Then each entry is an `InsertSegment` document command, in order, as `podcast segment insert` sends it, each with the version it resolved to. `start` and `end` are read when that entry runs, so `end` is the end of the timeline after the earlier entries have rippled (an intro at `start` and an outro at `end` on an 8 s episode with a 2 s intro and 2 s outro lands the outro at 10 s, ending at 12 s). Seconds are read the same way, on the timeline as the earlier entries left it. The result lists every entry's insert, the duration before and after, and `undo_steps`. Each entry of a real apply carries its own `history_head_id`: the head that entry left, read under the document lock from its own reply, so the heads are distinct and in order. A caller undoes the kit last entry first, guarding each step with that entry's head and requiring the head it gets back to be the previous entry's. A dry run has neither `undo_steps` nor per-entry heads.

**Apply route.** `POST /api/kits/apply` (host only, like the offer) takes `{path, kit_id, kit_version, client_id}` and returns the apply report (`kit_apply_tool`'s JSON, with each entry's `history_head_id`) from `submit_kit_apply`. It first re-runs the offer and refuses with 409 `kit_not_offered` unless the reason is `offer` and the kit is listed (the episode now has segments, or the kit became unusable). The check and the apply run under one in-process lock per project, so two concurrent requests apply once: the second waits, then gets `kit_not_offered`. It also refuses with 409 `kit_changed` when the newest kit version is not `kit_version` (the notice was stale). A kit saved again after that check but before the apply reads it is not caught. Refusals carry the service code in `X-Sharecut-Error-Code`: `kit_unknown` 404, `kit_not_offered` and `kit_changed` 409, a document conflict 409, `kit_apply_failed` and `project_write_failed` 500, every other code 400 (`kit_segment_missing`, `segment_hash_mismatch`). A failure after the first entry names how many entries landed; those stay applied and stay in History.

**Undo.** There is no compound document command, so a kit is one undo step per entry: undoing a three-entry kit takes three undos. A compound command would need a new payload, share-role handling and generated schemas for little gain at this size; it is listed under [Not built yet](#not-built-yet). A failure of the write itself after the first entry (a full disk, `project_write_failed`, a lock timeout, a document conflict) stops the apply with the same code and a message that names the entry (`Kit entry 2 of 3 (...) failed: ...`) and says how many earlier entries were applied; those stay applied, each its own undo step. Retrying the whole kit would insert them again, so undo them first or apply the rest by hand with `segment insert`. There is no resume argument yet.

An uncoded file failure during an entry stops the apply with `kit_apply_failed`. The message names the entry and counts earlier calls that completed. The failing entry may already have changed the episode, even when no earlier entries completed. Check the episode and History before retrying the kit; retrying can insert entries again. Raw filesystem diagnostics and paths are not included in this message.

**`--dry-run`.** Runs the same chain on a copy, entry by entry, so each report accounts for the ripples of the entries before it, and writes nothing: no journal row, no history step, no audio in `raw/`, and a project still under its retired entry-file name is not renamed. The project is read with `ProjectWorkspace.open(adopt=False)`.

**Offer.** `podcast kit offer PROJECT [--json]`, MCP `kit_offer_tool(project_path)` and `GET /api/kits/offer?path=` answer whether an episode should be offered the show kit, and which kits it can offer. All three call `report_kit_offer` in `services/document/kit_offer.py`, so the JSON and the codes are the same. The project is opened with `ProjectWorkspace.open(path, adopt=False)`: nothing is written or journaled, nothing is applied, and an invalid project is `project_unreadable` or `project_not_found`, as for drift. The report is `{"offer": bool, "reason", "kits": [{id, name, version, entries: [{segment_id, version, at, note}]}], "unusable": [{id, name, version, missing, problem}]}`; `kits` and `unusable` are always lists, sorted by name then id, and `version` is the kit's own version on a kit row and the resolved segment version (never null) on an entry. The first matching rule gives the `reason`:

| `reason` | When | `kits` / `unusable` |
|---|---|---|
| `no_clips` | the episode has no clip in `project.clips` | both empty |
| `already_has_segments` | any clip carries a `segment_ref` (something was inserted) | both empty |
| `no_kits` | the library has no readable kit (a kit whose newest version is damaged is left out; `kit list` still shows it `DAMAGED`) | both empty |
| `no_usable_kits` | no kit is usable | `kits` empty, `unusable` not |
| `offer` | at least one kit is usable (`offer` is true only for this reason) | `kits` not empty, `unusable` may be |

A kit (its newest version) is usable when every entry's segment version, the pinned one or the newest when `version` is null, is in the library and passes the cheap read: `segment.json` parses, the files exist and the sizes match. An unusable kit is listed under `unusable` with `missing`, the number of entries that are absent, fail that read or raise an `OSError` (each entry counts once, and an `OSError` is that entry's problem, with its message), and `problem`, naming the first. The offer does not hash audio; `kit apply` refuses a same-size change with `segment_hash_mismatch`, and it has other refusals the offer cannot predict (see Apply). "Not now" is a Studio concern kept per user in the browser; it is not stored in the project.

### Studio notice

When the host opens an episode and the offer is `offer`, the stage frame shows a notice, "Add your show's intro and outro?", that names the first kit's entries (segment names from the library, "Intro at start, Outro at end") with "Add them" and "Not now". Nothing is applied without the tap. "Add them" calls the apply route, then a toast says what went in and offers "Undo"; Undo takes back each entry in turn with `history_undo` and the head from the apply report, and stops, saying how many it undid, if the project changed meanwhile. "Not now" hides the notice for that episode and kit on this device. The offer is read again when the project opens, when its first clip arrives, when a pipeline run ends and after an apply or an undo. Guests never see it.

**Host MCP tools.** `kit_list_tool`, `kit_show_tool`, `kit_save_tool` (`name`, `entries` as `{segment_id, at, version?, note?}`), `kit_apply_tool` (`project_path`, `kit_id`, `dry_run`) and `kit_offer_tool` (`project_path`) call the same functions as the CLI (`segments/kit_summary.py`, `submit_kit_apply` in `services/document/kit_apply.py`), so the codes are the same, including for `kit save` input: one parser (`segments/kit_summary.py`) turns `ID[@VERSION][:AT]` on the CLI and `{segment_id, at, version?, note?}` in the tool into an entry, and a version that is not a whole number from 1 is `segment_version_invalid` on both. `note` is set through the tool only; the CLI has no flag for it. `submit_kit_apply` lives in `services/document/kit_apply.py`. They are host only: none is on the guest allowlist, and `InsertSegment` stays out of every share role's commands.

**Doctor.** `podcast doctor` warns for each kit (newest version) whose segments are missing from the library, naming up to five of them, and for a kit that cannot be read. It reads only `kit.json` files and segment folder names, so it stays cheap, and a segment that is present but damaged is reported by the segment check above, not by the kit line (`kit apply` refuses it with `segment_unreadable` or `segment_hash_mismatch`); the fix line says to import the segments or the kit's `.sharecutkit` file again.

## Doctor

`podcast doctor` checks the newest version of each segment in the library by looking at `segment.json` and each audio file's presence and size, without reading the audio, so the support bundle (which runs the same checks) stays cheap. `podcast doctor --deep` also hashes the audio. It prints a `[warn]` line for each damaged segment (at most five, then a count of the rest). The fix line is the same text `podcast segment list` prints: import the segment again, which stores a new version and keeps the older ones; `podcast segment remove ID` is named only when the segment has no older version, because it deletes every version. A segment removed while doctor runs is left out. An absent or intact library prints nothing. A damaged segment does not fail doctor. Older versions are not checked.

- Studio screens to rename a segment or to export and import a kit (Studio lists, auditions, removes, saves from a selection, inserts, and exports and imports a segment file, see [Studio](#studio)). Dropping a file anywhere on the Studio window and opening a `.sharecutseg` from a phone's share sheet are not built either.
- A compound document command that makes a whole kit one undo step.
- `podcast segment export ID... -o FILE.sharecutkit` and `segment import FILE.sharecutkit` (the kit commands do this, see the kit section above).
- Capturing a transcript or a chapter title.
- Setting `duck_under_dialogue` or `chapter_title` (no command writes them yet).
- Per-clip gain and mute-region data beyond what is rendered into the audio.

## Decisions

Settled with slice 2, each with its reason.

- **Name-derived id stays.** No rename operation exists, so a rename is deliberately a new segment, and `segment_ref` also holds the content hash, so a later slice can relink by content.
- **`schema_version` stays `Literal[1]` with unknown fields refused; a new field is schema 2 on purpose.** Beta has no libraries worth carrying, and a reserved extensions object would hide format changes from older builds. `content_sha256` is now pinned by a golden-hash test, so a field that changes every stored hash fails a test instead of passing unseen.
- **One role and one fader per segment.** Capture collapses a mixed selection to its first clip's track and Insert maps lanes by that role; a per-lane table is a schema 2 change when capture can write one.
- **No sample rate or channel count in `segment.json`.** Insert probes the copied file anyway to build its source, so declaring them would only add a second truth.
- **Trust is integrity only, with no signature.** Segments move between people as files the user chooses to import; a signature needs a key story that does not exist yet. Insert re-checks the hash on its own copy.
- **`capture.py` moved to `services/document/segment_capture.py`.** It imports engines and the workspace service, and `services/` is where the new Insert code lives.
- **Dedupe compares FLAC bytes and stays that way.** A different ffmpeg build making a new version is harmless, since each version has its own content hash and a `segment_ref` points at one version.
- **A kit names segments, it does not contain them.** The library stays the one home of audio, so editing a segment (a new version) reaches every kit that names it by id, and a pinned `version` is the way to freeze one. A bundle copies the audio in so a kit travels on its own.
- **Kit conflicts mirror segment versions.** There is no overwrite: the same name with other entries is the next version, and `--on-conflict skip` exists for the person who wants their own list kept.
- **One undo step per entry.** A compound `ApplyKit` document command was weighed and left out: it would add a payload, a capability row, share-role tests and generated schemas, and the per-entry steps are each journaled, visible in History and individually undoable.
