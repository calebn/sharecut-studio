# Decisions

A product or design decision lives in the doc that describes the behaviour it
governs, as a short decision block next to that behaviour. This page explains
the block and lists every block in `docs/`. The list is generated by
`scripts/decisions_index.py`, so edit the blocks, not the table.

A separate decision file would give two descriptions of one rule that drift
apart. A block keeps the rule, its evidence and its checks in one place, and
the index makes them findable.

## When to write a block

Write a block when the owner settles a product or design question that the
next contributor could reasonably reopen: a default, a permission, a listening
rule, an input convention, or a process rule. Don't write one for an
implementation detail that a test already explains.

## The block

A block is a heading followed directly by an HTML comment. The comment does
not render, so the doc reads as before.

```markdown
### Decision: Bleed handling defaults to auto

<!-- decision
id: D-bleed-auto-mode
status: accepted
date: 2026-10-06
decided-by: calebn
evidence:
- #1053 owner listening, round 1: the copy still read as an echo
enforced-by:
- tests/test_bleed_attenuation.py::test_foreign_copy_on_a_gated_lane_is_muted
- docs-sync: decision-bleed
supersedes: D-bleed-attenuate-everywhere
-->

The doc's normal explanation of the behaviour follows.
```

The heading starts with `Decision: `, `Proposed decision: ` or `Superseded
decision: `, matching `status`. Each field is one `key: value` line, and
`evidence` and `enforced-by` are lists of `- ` lines. A comment cannot contain
two hyphens in a row.

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | `D-` plus kebab-case. Stable once merged. |
| `status` | yes | `proposed`, `accepted` or `superseded` |
| `date` | yes | The day the owner decided, `YYYY-MM-DD` |
| `decided-by` | yes | GitHub login of the person who decided |
| `evidence` | no | Issues and PRs (`#N`), owner listening or phone verdicts with a short quote, lab numbers, and patterns that failed and were revised |
| `enforced-by` | see below | Automated checks: `path::test name`, `docs-sync: <rule-id>` or `make <target>` |
| `manual-review` | see below | Who reviews and when, for a rule no automated check can prove |
| `enforcement` | see below | `pending #N`: the issue that builds the checks |
| `supersedes` | no | The id this decision replaces |
| `superseded-by` | with `superseded` | The id that replaced this one |

An accepted decision names at least one of `enforced-by`, `manual-review` or
`enforcement: pending #N`. Prefer a test that fails when the behaviour changes.
`manual-review` is for rules that only a person can judge, and it says why.
Only an accepted decision can have pending enforcement.

## Lifecycle

1. **Proposed.** A PR adds the block with `status: proposed`, its evidence and
   the open question. The behaviour may not exist yet.
2. **Accepted.** The owner approves the decision in the issue or PR review. The
   PR sets `status: accepted` and names its enforcement. When the owner applies
   a default and leaves an override open, the block is accepted and its prose
   says what the owner can still override.
3. **Superseded.** A later decision replaces it. The old block stays in place,
   next to its replacement, with `status: superseded`, `superseded-by` and a
   `Superseded decision: ` heading. The new block names it in `supersedes`. Its
   prose says what changed and why, so the doc keeps the history.

A change to code that a decision governs updates that decision's doc, or its
commit carries `Docs-Sync-Waive: decision-<area> <reason naming the decision id>`.
The `decision-*` rules in `contracts/docs-sync.json` map each area's code to its
doc ([contributing.md § Docs in sync](../contributing.md#docs-in-sync)).

## Checks

- `make decisions-index` rewrites the table below.
- `make decisions-index-check` and the `decisions-index` pre-commit hook fail
  when a block is invalid or the table is stale.
- `tests/test_decision_records.py` runs the same checks in CI. It fails when an
  accepted decision names no enforcement, a listed test, rule or make target
  does not exist, a supersession link is broken or one-sided, or two blocks
  share an id.
